# 单用户服务端存储（Docker）

## 架构

工作簿和运行选项沿用现有 JSON 格式，SQLite 负责事务和修订版本。数据库是权威数据源；新设备登录后自动加载同一份工作簿及模型、TTS 配置，不再恢复旧浏览器数据覆盖服务器。手机/桌面布局偏好仍可按设备保存。

- `/data/chainflow/personal.sqlite` 位于现有 `app-data` Volume；WAL、FULL 同步和版本比较确保提交可靠。
- 工作簿与配置独立编号，旧版本写入返回 HTTP 409。不会自动覆盖另一台设备的数据。
- API Key 使用 AES-256-GCM、随机 nonce、目标地址及用途绑定加密；主密钥与数据库分离。
- 主密钥来自只读 Docker Secret `/run/secrets/chainflow_master_key`。宿主机文件默认 `local-only/secrets/master-key`，由 Windows ACL 限制访问，不进入 Git 或镜像。
- 账户与会话仍在 `auth.json`，原有 Codex 登录卷保持不变。所有业务 API 仍需登录，写入仍需 CSRF。
- 配置 GET 仅返回 `modelKeyConfigured` / `ttsKeyConfigured`，不能读取完整密钥。模型设置提供保存、删除、保存并测试；TTS 设置提供保存、删除及测试连接。
- 密钥只在构造上游请求时解密。客户端传入的地址和 Authorization 不能改写服务器保存的目标或密钥。
- 外部模型/TTS 沿用已审阅 HTTPS 域名白名单，禁止 URL 凭证、查询、内网地址和重定向。本地模型限定 LM Studio 1234 / Ollama 11434，本地外部 TTS 限定 8880 / 8881。

Node 原生 SQLite 不增加 npm 依赖；Node 22/24 当前仍会提示实验性 API，但项目固定的 Docker Node 24 支持本次使用的接口。参见 [Node 24 SQLite](https://nodejs.org/docs/latest-v24.x/api/sqlite.html)。

## 首次迁移

新部署或首次升级到此版本，先在项目目录执行 `node scripts/init-master-key.mjs`，再重建 app。已有主密钥会保留；如数据库已存在但主密钥丢失，应从备份恢复原密钥，不能重新生成替代。自定义文件路径时同时设置 Compose 的 `CHAINFLOW_MASTER_KEY_PATH`。

1. 更新后先在**原来保存着工作簿的 Windows 浏览器及访问地址**登录；不同 IP/域名的浏览器存储互不相通。
2. 点击“备份并迁移此浏览器数据”。会下载无密钥 JSON 备份，上传所有工作表、列配置、运行选项和历史结果；可记忆的旧模型密钥会加密上传。
3. 成功后移除旧浏览器连接中的明文密钥，保留原工作簿副本。旧 TTS 密钥原本只存在旧页面内存，无法从关闭的旧页面自动恢复，需要在新配置窗口重新输入一次。
4. 等待“已保存到服务器”，再在 iPhone 登录/刷新。不要在空设备上先选择“创建全新空白工作簿”。
5. 其他浏览器若有额外旧工作簿，先导出 JSON，再使用现有导入入口合并为新工作表，不覆盖服务器。

不会迁移或清空原浏览器数据后再尝试保存；迁移失败时原数据保留。历史浏览器里尚未迁移的旧明文密钥不会被本次升级自动删除；确认其配置已迁移后，可清理旧连接条目或旧站点数据。

## 自动保存、冲突与离线

单元格、行列、工作流、拆句以及 AI 最终结果均经现有工作簿序列化自动保存。只有服务器确认提交后才显示已保存。保存失败时显示未保存、允许重试和导出，保留不含密钥的本机待同步副本；这份副本是恢复用草稿，不是权威版本。

刷新发现草稿时先显示恢复提示，可导出后通过 JSON 导入合并。冲突不会自动重试覆盖；请保留当前副本，再重新加载服务器版本。第一版不做实时协同或自动三方合并。设备切换前请等待保存完成；另一台已经打开的页面需刷新以加载更新。

原工作流引擎及取消语义保持不变：关闭页面会停止当前客户端调度，未完成任务不承诺后台继续运行；已经完成的结果触发保存，未确认提交的结果由恢复草稿保留。fnOS 是否逐块转发 SSE 取决于原网关，本轮不重写 NAS 软件。

## 备份和恢复

完整备份包含：`personal.sqlite`、`auth.json`、`master-key`、校验清单。目前应用无服务端附件文件；音频不落盘。如需迁移 Codex 登录，则另外备份 `codex-login` Volume（属于敏感凭证）。

在 Windows 项目目录执行（目标必须是新目录）：

```powershell
./scripts/backup-personal.ps1 -Destination F:\ChainflowBackups\2026-10-09
```

脚本通过 SQLite 在线备份接口获取一致性快照，复制主密钥和账户文件，验证校验和、数据库完整性以及全部已保存密钥能否解密。宿主机备份目录限制为当前 Windows 用户和 SYSTEM。备份会包含解密主密钥，必须将**整套备份**视为敏感文件，不可上传 GitHub。

恢复会短暂停止 **Chainflow app**，不会停止 Kokoro 或其他服务；先确认允许停机，再执行：

```powershell
./scripts/restore-personal.ps1 -Backup F:\ChainflowBackups\2026-10-09 -ConfirmStop
```

恢复前验证备份，并另做当前数据的完整备份；原 SQLite/WAL/账户文件也归档保留，然后恢复匹配的主密钥和数据库。不要手工只覆盖 `.sqlite` 而遗留旧 WAL 文件。恢复失败时不会删除备份，容器可能保持停止，请根据脚本错误处理。恢复后所有设备刷新页面再编辑。

数据库或主密钥缺失/不匹配会拒绝启动，不会自动生成另一把主密钥尝试打开旧数据库。

## 手机验收

2026-10-09，用户确认 Windows 与手机飞牛 App 远程使用验收通过。飞牛路径为 iPhone 飞牛 App → FN Connect → NAS 的 fnOS 统一网关 → 已有 Chainflow 网关应用 → Windows Docker 3003；NAS 负责入口转发，工作簿、加密配置及 Codex 登录仍保存在 Windows。现有网关源码/FPK 在另一个项目中维护，本仓库不包含其安装包，也不要求修改已运行的 NAS 应用。此入口能返回最终结果，但尚不能逐块显示 Chainflow 生成文本。

1. Windows 完成迁移，新建或修改一条记录，等待保存；手机飞牛入口登录/刷新查看。
2. 手机修改同一记录，等待保存；Windows 刷新查看。
3. Windows 保存模型密钥并测试；手机刷新后直接运行 API 模式，不填 key。
4. Windows 保存外部 TTS 配置并测试；手机刷新后朗读（火山免配置模式没有 key）。
5. 两台设备同时编辑：后保存的旧版本应报冲突，保留其副本，不应覆盖先保存的版本。
6. 临时断网编辑：显示未保存，联网后重试；刷新时能导出未同步副本。
7. 退出登录后工作簿/配置 API 返回 401；刷新或容器重启后数据与配置仍在。
